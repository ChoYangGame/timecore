## 01 팀 구성과 공통 AI 활용 원칙

### 1.1 역할 분담

| 팀원 | 담당 | AI를 사용한 영역 |
|---|---|---|
| 개발 | 게임 설계·구현·빌드·배포 | 코드 생성·수정, Unity 에디터 조작, Play 모드 실측 검증, 문서화, 코드 리뷰 |
| 디자인 | 아트 방향·2D 에셋·사운드 | 맵·캐릭터·보스·무기·이펙트 생성, 영상 생성 후 프레임 선별, 크로마키 후처리, BGM 작곡 |

두 사람은 **낱장 투명 PNG + 프레임 순서·권장 재생 속도** 규약으로 자산을 주고받았고,
개발 쪽은 받은 아트에 맞춰 판정과 연출을 다시 맞추는 방식으로 통합했다(05장).

### 1.2 양쪽이 공유한 4가지 원칙

1. **기준을 먼저 문서로 고정한다.** 디자인은 프로젝트 설정 MD와 승인 이미지, 개발은 `CLAUDE.md`(프로젝트 규칙 파일)를 AI 입력의 최상위 제약으로 뒀다.
2. **AI 출력은 완성품이 아니라 후보 데이터다.** 생성 원본은 Drafts/Source로 분리하고, 검증을 통과한 것만 최종 폴더·최종 커밋에 넣는다.
3. **검증은 추정이 아니라 실측으로 한다.** 디자인은 알파·바운딩박스·잔여색 수치 검사, 개발은 Play 모드 수치 측정과 화면 캡처, 빌드 산출물의 바이트 단위 대조를 사용했다.
4. **실패를 기록한다.** 되돌린 결정과 오진단을 `docs/AI_LOG.md`와 에셋별 README에 남겼다. 이 문서에서 가장 설명 가치가 있는 부분도 그 기록에서 나왔다.

### 1.3 기준 우선순위 (양쪽 공통)

| 우선순위 | 근거 | 적용 원칙 |
|---:|---|---|
| 1 | 현재 대화의 최신 사용자 지시 | 기존 문서와 충돌하면 최신 명시 지시를 우선 |
| 2 | 최종 승인 이미지·기준 파일 / 프로젝트 규칙 파일 | 형태·비율·색상·시점·재질 / 기술 제약을 고정 |
| 3 | 프로젝트 설정 MD | 아트·애니메이션·맵·UI 공통 규칙 |
| 4 | 이전 미확정 아이디어 | 참고만 하고 자동 채택하지 않음 |

### 2.2 Unity MCP로 실제로 사용한 명령

개발 쪽 AI 활용의 핵심은 "코드를 써 준다"가 아니라 **에디터를 직접 조작하고 그 결과를 수치로 되읽는다**는 점이다.

| 명령 | 용도 | 실제 사용 예 |
|---|---|---|
| `Unity_GetConsoleLogs` | 컴파일·런타임 에러 확인 | 모든 작업 종료 시 "에러 0건" 확인. 빌드 성공 판정의 근거 |
| `Unity_RunCommand` | 임시 C# 스크립트 컴파일·실행 | Play 모드 진입, 강제 피해 적용, 프레임 계측, 임포트 설정 변경 |
| `Unity_ManageGameObject` | 오브젝트 생성·컴포넌트 부착·속성 조회 | HUD 배치, `BgmManager` 부착, 버튼 목록 조회 |
| `Unity_ManageScene` | 씬 하이어라키 조회·저장 | UI 구조 파악, 변경 후 저장 |
| `Unity_Camera_Capture` / `ScreenCapture` | 실제 렌더 화면 캡처 | VFX 값 보정, 배경 아트 가독성, 무기 위치 확인 |
| `Unity_ManageAsset` / `FindProjectAssets` | 에셋 조회 | 프리팹 경로 확인 |

## 03 개발 파트 — AI를 코드와 에디터에 사용한 구조

### 3.1 작업 루프 구조

개발은 매 작업을 아래 6단계 루프로 돌렸다. 3~5단계가 **한 세션 안에서 반복**된다는 점이 이 프로젝트 개발 파트의 특징이다.

| 단계 | 주체 | 내용 |
|---:|---|---|
| 1 | 사람 | 원하는 결과와 **하지 말 것**을 함께 지시 |
| 2 | AI | 구현 방식을 먼저 제시(범위가 큰 작업), 사람이 승인 |
| 3 | AI | `.cs` 작성·수정 (Auto Refresh로 Unity가 자동 컴파일) |
| 4 | AI | `Unity_GetConsoleLogs`로 컴파일 결과 확인 |
| 5 | AI | `Unity_RunCommand`로 Play 모드 진입 → **수치 실측** + `Camera_Capture` |
| 6 | AI | 결과를 `docs/AI_LOG.md`에 append (실패·오진단 포함) |

> **왜 실측을 루프에 넣었나**
>
> 이 프로젝트에서 AI가 가장 자주 틀린 지점은 문법이 아니라 **"눈으로 안 본 값"** 이었다.
> 이펙트 색, 아트 크기, 무기 위치처럼 화면에서만 판단되는 값은 첫 시도가 거의 항상 빗나갔다.
> 그래서 캡처와 수치 측정을 선택이 아니라 루프의 고정 단계로 만들었다.

### 3.2 AI에 준 상시 지시 — `CLAUDE.md` (가장 중요한 프롬프트)

일회성 프롬프트보다 효과가 컸던 것은 **저장소에 커밋된 규칙 파일**이다. Claude Code가 매 세션 시작 시 자동으로 읽으며, 프로젝트의 기술 제약과 사고 실패 이력이 누적된다. 아래는 실제 내용 발췌다.

```markdown
## 기술 제약 (위반 시 빌드가 깨짐)

- 타깃은 Unity 6 / Web(WebGL) 빌드다. WebGL이 지원하지 않는 API를 쓰지 말 것:
  - 멀티스레딩 (Thread, Task.Run, Parallel)
  - System.IO 파일 접근 → 저장은 PlayerPrefs만
  - 소켓, System.Net 기반 통신
- 빌드 용량 = 로딩 시간이다. 새 패키지나 에셋 도입 전에 반드시 먼저 물어볼 것.
- 목표 사양은 저사양 노트북 브라우저다. 최적화보다 안정적 프레임이 우선.
- URP 2D Light는 적이 많아지면 비싸다. 분위기는 스프라이트 색조로 처리.

## Unity 애셋 파일 외부 편집 금지 (하드 룰)

- Unity 에디터가 켜져 있는 동안 .unity / .prefab / .asset 파일을
  외부 텍스트 편집으로 수정하지 않는다.
- 씬 직렬화 값을 바꿔야 하면 SerializedObject 주입 경로를 사용한다.
- 이유: Unity가 외부 변경을 감지해 모달 다이얼로그를 띄우는데,
  모달은 MCP로 닫을 수 없어 세션이 통째로 막힌다. 2026-08-05에 8분 이상 차단됐다.

## Unity 컴파일 처리

- Auto Refresh는 켜져 있다. Ctrl+R 요청은 효과가 없으니 하지 마라.
- DLL 타임스탬프 폴링 절대 금지.
- 컴파일 결과는 Unity_GetConsoleLogs로만 확인한다.
- Unity_RunCommand의 빌드 결과가 "failed"여도 GetConsoleLogs의 에러가 0건이면,
  Build/ 폴더 타임스탬프와 용량으로 실제 성공 여부를 판단한다.

## 작업 방식

- 확장성보다 지금 돌아가는 것이 우선. 완벽한 아키텍처를 제안하지 말 것.
- 먼저 요청하지 않는 한 리팩터링하지 말 것.
- 코드는 클래스 단위로 완결되게, 어느 GameObject에 붙이는지 명시할 것.

## 필수: 작업 세션 종료 시 로그 기록

- 실패한 시도, 되돌린 결정, 오진단은 반드시 기록한다.
- WebGL 제약 때문에 내린 결정은 그 제약을 명시적으로 적는다.
```

> **이 파일의 각 줄은 대부분 사고 이후에 추가됐다.**
> "외부 편집 금지"는 8분 세션 차단 뒤, "DLL 폴링 금지"는 stale 캐시 오진단 뒤,
> "폰트는 Update Atlas Texture로만"은 씬의 TMP 참조 11개가 전멸한 뒤 추가됐다.
> 즉 이 파일 자체가 **AI 실패 사례의 재발 방지 장치**로 성장했다.

### 3.3 개발 파트 주요 프롬프트와 지시 설계

실제로 사용한 지시는 네 가지 패턴으로 정리된다.

#### (1) 사양을 표처럼 못박는 지시 — 초기 구조 구축

```text
Player: 흰 사각형, PlayerMove + Health + AutoAimShooter,
        BoxCollider2D, Rigidbody2D(Kinematic), 태그 Player
Enemy 프리팹: Enemy + Health, BoxCollider2D(trigger), Rigidbody2D(Kinematic), 태그 Enemy
Bullet 프리팹: Bullet + BoxCollider2D(trigger)
Main Camera: CameraFollow, 배경색 #1B2436
색상: 플레이어 #6FD8E0, 적 #A8322D, 총알 #F2EFE9
스크립트가 타입으로 인식 안 되면 바로 나에게 알려줘.
```

#### (2) **하지 말 것**을 함께 주는 지시 — 범위 폭주 차단

```text
시대를 4개(원시/중세/현대/미래)로 확장한다.
[F. HP 스케일링] 초기값은 완만하게: 1.0 / 1.2 / 1.45 / 1.75
 (웨이브 단축으로 플레이어 증강 획득이 줄었으니 세게 잡지 마라)

[하지 말 것]
 Boss.cs 패턴 시대별 분리, 새 적 타입, 새 프리팹 추가,
 ScriptableObject 도입, BackgroundGrid.cs, 요청하지 않은 리팩터링
```

```text
EraManager.cs 미래 EraConfig의 색만 바꿔줘.
enemyColor: 짙은 마젠타 계열 / bossColor: 밝은 마젠타/바이올렛 계열.

다른 건 아무것도 건드리지 마라.
```

#### (3) 검증 절차를 지시에 포함 — "됐다"를 믿지 않는다

```text
deploy.bat 실행 / dist/ 총 용량 알려줘

```

```text
씬 값은 SerializedObject로 주입해줘. 파일 직접 편집은 하지 말고.
```

```text
구현하는 작업이야 ... 구현 방식을 먼저 알려주고 확인받은 뒤 진행해줘
```

#### (4) 감각으로 말하고 원인은 AI가 찾게 하는 지시 — 가장 자주 쓴 형태

```text
"이팩트들이 그냥 너무 네모네모 너무 조잡한데"
"뭔가 지금 레이저 기믹은 그냥 히트 박스만 표시하는 느낌이잖아"
"아냐아냐 다 보이게 하고 싶은게 아니라 움직였을때 끝까지 안보인다는거야"
"근접무기 위치가 몸에 너무 겹쳐져있어 손에 잡고 휘두르는 듯한 연출을 위한거니까
 좀 떨어뜨려서 휘두르게 해줘"
"그 지렁이 게임 알아? io게임 말이야 거기선 로그인 안하고 이름만 적고 랭킹이 뜨던데"
```

> 이 형태에서는 AI가 **먼저 재현하고 수치로 원인을 특정한 뒤** 고치도록 했다.
> 예: "몸에 겹친다" → 플레이어 스프라이트 실측 1.63×1.77유닛(반지름 약 0.8)인데
> 무기를 쥐는 지점이 0.45라 손이 몸 한가운데 있었고 자루가 0.61 더 뒤로 뻗는 구조임을
> 수치로 확인한 뒤 1.05로 조정했다. 짐작으로 값을 흔들지 않았다.

### 3.4 검증 구조 — 무엇을 어떻게 측정했나

| 검증 축 | 방법 | 실제 사례 |
|---|---|---|
| 컴파일 | `Unity_GetConsoleLogs` 에러 수 | 모든 세션 종료 시 "에러 0건" 명시 |
| 게임 로직 | Play 모드 자동 드라이버 + 수치 비교 | 4시대 완주 시 보스 HP **4000/4800/5800/7000** = 정확히 ×1.0/1.2/1.45/1.75 |
| 판정 정합 | 좌표·거리 실측 | 감속 지대 안팎 적 1초 이동 **1.100 / 2.201 = 비율 0.500**(설정 0.50) |
| 시각 | `Camera_Capture` 반복 캡처 → 값 수정 → 재캡처 | VFX 개편에서 3회 반복, 배경 아트·무기 위치 확인 |
| 성능 | 같은 루프에서 기능만 껐다 켜기 | 이펙트 OFF 평균 305 FPS / ON 330 FPS → **비용이 측정 노이즈 이하** |
| 용량 | 빌드 산출물 바이트 비교 | 보스 12패턴 + VFX 개편 후 **+20,373 bytes**(새 에셋 0이라 코드 몫뿐) |
| 배포 | `curl -I`로 `Content-Length` 대조 | 산출물 4종이 로컬과 **바이트 단위 전부 일치** 확인 |
| 폰트 | 렌더 후 `characterInfo[i].fontAsset` 전수 검사 | 가시 문자 **162자 전부 Pretendard SDF, 폴백 0건** (`HasCharacter()`만으로는 못 믿는다) |

### 3.5 WebGL 제약이 설계를 바꾼 지점

기술 제약이 AI에게 준 지시의 내용을 바꾼 사례다. 이 프로젝트에서 가장 설명 가치가 있는 판단들이다.

| 문제 | 일반적 해법 | 우리가 택한 것 | 결과 |
|---|---|---|---|
| 타격 이펙트 | `ParticleSystem` | 조각 96→160개 **풀 + 단일 Update** 배열 순회 | 인스턴스마다 Update·GC 없음. 빌드 증가 **0 byte** |
| 이펙트 텍스처 | 에셋스토어 VFX 팩 | Dot·Ring·GlowBar 등 **6종을 코드로 런타임 생성**(64×64, PPU 64) | 빌드 증가 **0 byte**, RAM 약 96 KB |
| 효과음 16종 | 무료 사운드 팩 | 사인·사각·톱니·노이즈 + 포락선으로 **코드 합성** | 빌드 증가 **0 byte**, RAM 765 KB |
| 온라인 랭킹 | 서드파티 리더보드 SaaS | **같은 도메인**에 Vercel 서버리스 `api/` + Upstash Redis | CORS 문제가 발생 자체를 하지 않음 |
| 통신 | 소켓 / `System.Net` | `UnityWebRequest` (WebGL의 유일한 정식 수단) | 규칙 위반 없음 |
| 저장 | 파일 IO | `PlayerPrefs` | WebGL 금지 API 회피 |
| 충돌 판정 | Collider / 물리 | **위치 클램프 + 매 프레임 거리 질의** | 물리 연산 0. 적 40 × 존 3 = 프레임당 수십 회 비교 |
| 아레나 벽 | 콜라이더 벽 | 배경 스프라이트 실측 bounds에서 경계 역산 | 시각적 벽 = 논리적 벽 항상 일치 |
| BGM 4곡 | 원본 MP3 그대로 | 모노 강제 + Vorbis q0.4, 그 시대에만 로드 후 즉시 언로드 | 6.4 MB → **2.0 MB (-69%)** |

### 3.6 인게임 "AI 디렉터"는 규칙 기반이다 (명시)

게임 안에는 플레이 상황에 따라 난이도를 조정하는 `AnomalyDirector`가 있다. **이것은 학습 모델이 아니라 순수 C# 규칙 엔진이며, 외부 의존성이 없다.** 대회 요건이 요구하는 AI가 "개발 도구로서의 AI 활용"이고, 저사양 브라우저 + 빌드 용량이 최우선 제약이므로 추론 런타임을 게임에 넣지 않기로 초기에 결정했다.

| 규칙 | 감지 조건 | 개입 |
|---|---|---|
| 1 위기 | 플레이어 HP 비율이 임계 이하 | 압박 완화 (유일한 구제책) |
| 2 과잉 화력 | 처치 속도가 과도 | 다른 시대 적 난입 |
| 3 전선 정체 | 생존 적 비율 ≤ 0.25 (화면이 한산) | 밀도 상승 |
| 4 전선 고정 | 평가 간격 동안 플레이어 이동 < 4유닛이 2회 연속 + 적 충분 | **그 자리에 감속 지대 배치** |

- 지표는 매 프레임이 아니라 `evaluateInterval`마다 1회만 계산한다(저사양 브라우저 대비).
- 규칙 1~3은 "적을 얼마나 낼지"를, **규칙 4만 공간을 바꾼다.**
- 개입 판단은 전부 콘솔에 기록되며, 판 종료 시 `OnDestroy`에서 요약이 자동 출력된다.
- 실측 예: 규칙 4가 `t=35.0s`에 자연 발화 — `판단: 전선 고정 → 개입: 플레이어 이동 0.0 < 4.0 ×2회 → 감속 지대 배치` (생존 적 21/40).

> **AI에게 상태를 강제 주입할 수 없었던 것이 오히려 검증을 강하게 만들었다.**
> MCP가 `System.Reflection`을 차단해 디렉터의 사적 상태를 직접 조작할 수 없었고,
> 그래서 조건이 **자연히 성립하도록 플레이 상황을 만들어** 관찰하는 방식으로 갔다.

### 3.7 개발 파트에서 AI가 틀린 사례와 대응

| 사례 | AI의 오판 | 실제 원인 | 대응 |
|---|---|---|---|
| 스크립트 인식 실패 | MCP 5개 경로로 우회 시도, 전부 실패 | `Library/ScriptAssemblies`의 stale DLL 캐시 | 사람이 에디터 재시작. 이후 CLAUDE.md에 "DLL 폴링 금지" 명문화 |
| 세션 8분 차단 | 씬 파일을 텍스트로 직접 편집 | Unity가 외부 변경 감지 → **모달은 MCP로 못 닫는다** | `SerializedObject` 주입 경로로 전환 + 하드 룰 승격 |
| 폰트 참조 11개 전멸 | Font Asset Creator로 새 애셋 생성 | Unity 6에서 타입이 `TMP_FontAsset`이 아닌 다른 타입으로 생성됨 | git 복구 + `ImportAsset(ForceUpdate)`. "Update Atlas Texture로만" 규칙화 |
| 아레나가 1.63배 크게 | Max Size로 축소된 실제 픽셀(2048)로 PPU 계산 | Unity는 축소돼도 **원본 해상도(3344px) 기준**으로 월드 크기를 고정 | 원본 기준 재계산(PPU 134) |
| "그림이 짤린다"를 오해 | 아레나 크기를 줄임 | 카메라가 **걷는 영역**으로 클램프돼 테두리 장식이 밀려남 | `Rect`(로직) / `VisualRect`(카메라) 분리 |
| 이펙트 색 3연속 빗나감 | 눈으로 안 보고 값을 잡음 | 흙바닥과 같은 갈색 / 새까만 블록 / 크기·알파 역방향 | `timeScale=0.1` + 캡처 3회 반복으로 보정 |
| 감속 지대가 안 보임 | 스프라이트 로드 실패를 의심 | `timeScale=0`으로 얼려 페이드인이 진행되지 않아 알파 0 | 시간을 흘린 뒤 재측정 |
| "사망음이 안 난다" | 효과음 배선 오류를 의심 | MCP 호출 사이에 게임이 계속 돌아 **이미 죽은 대상**을 다시 때림 | `timeScale=0`으로 얼린 뒤 재측정 → 정상 2보이스 |
| 장판 알파가 안 올라감 | 코드 기본값만 수정 | **프리팹에 옛 값이 직렬화**돼 코드 기본값을 덮고 있었음 | `SerializedObject`로 프리팹 값 주입 |
| 빌드 "failed" 반복 | 빌드 실패로 보고 | Sentis 패키지 셰이더 **경고**를 실패로 오보고 | 에러 0건 + 산출물 타임스탬프·용량으로 성공 판정 규칙화 |

### 3.8 코드 리뷰에도 AI를 사용했다

- 리뷰 원문은 `docs/reviews/YYYY-MM-DD-N회차.md`에 **요약 없이 전문** 보관한다.
- 판단·추적은 `docs/REVIEW_LOG.md`에서 관리하며, 지적별로 채택/기각/보류와 해결 커밋 해시를 남긴다.
- 1회차(2026-08-02): 지적 17건 중 **채택 10 / 기각 4**.
- 기각 사유를 남기는 이유는 **같은 지적이 다음 리뷰에 다시 올라오는 것을 막기 위해서**다. 프로젝트 규칙에도 "리뷰 요청 시 REVIEW_LOG를 먼저 읽고 이미 기각·보류된 항목을 다시 제안하지 않는다"로 명문화했다.

## 04 디자인 파트 — AI를 아트·사운드에 사용한 구조

> **디자인 파트가 사용한 AI는 세 가지다.**
> 맵·캐릭터·보스·무기·장판·배경의 **정지 원화는 전부 Codex(GPT-5.6 Sol, reasoning high)** 로 생성·편집했고,

### 4.1 단계 분리

생성형 AI의 결과를 즉시 채택하지 않고, 각 단계에서 사람이 확인할 수 있는 중간 산출물로 남겼다.

| 단계 | 구분 | 입력·처리 내용 |
|---:|---|---|
| 1 | 기준 입력 | MD·승인 이미지, 최신 사용자 지시 |

| 3 | AI 생성 | Codex(GPT-5.6 Sol, high) 정지 원화 · Higgsfield Seedance 2.0 Fast 4초 영상 · Suno BGM |

>
> AI 출력은 완성품이 아니라 후보 데이터다. 디자인 마스터와 규격 검증을 통과한 결과만
> 최종 폴더에 저장하고, 생성 원본은 Drafts 또는 Source로 분리한다.

### 4.2 AI에 맡긴 일 / 사람이 결정한 일

**AI에 맡긴 것**

**사람이 결정한 것**

| 장판 | 평면성, 화면 제한 크기, 열린 중심 | 4종 바닥색 가독성·원형/타원형 비율 |

> **실패를 사전에 이름 붙이기**
>
> `no motion blur` 만으로는 충분하지 않았다. 실제 프롬프트에서는 camera motion, zoom,
> perspective change, detached trail, bloom, light spill, extra limbs, disappearing weapons,
> design morphing 등 **실패 유형을 구체적으로 나열**했다.

### 4.5 맵 제작

4개 맵은 시대 차이를 보여주면서도 같은 게임의 전투 배경으로 쓸 수 있도록 **공통 레이아웃 제약**을 적용해 생성했다. 모든 결과물은 3344×1882 RGB이며 중앙 전투 공간과 가장자리 장식 구조를 공유한다.

**공통 지시**
- 높은 3/4 탑뷰의 16:9 전투장, 카메라 각도와 수평을 일정하게 유지
- 플레이어·몬스터·장판이 겹치는 중앙부는 넓고 평평하게 비우고 큰 장애물은 가장자리에
- 중앙에는 시대 식별 상징만, 텍스트·UI·캐릭터·몬스터는 생성하지 않음
- 모서리와 외곽에만 시대별 소품을 집중시켜 전투 가독성과 배경 정보량을 함께 확보

```text
2D top-down action roguelite battle arena, 16:9.
High 3/4 top-down view, fixed horizontal camera.
Keep the central combat area wide, flat, and unobstructed.
Place large props and environmental details only around the edges.
Use one clear era symbol at the center.
No character, monster, UI, text, logo, or gameplay effect.
Preserve the same composition across all four eras;
change only the era-specific materials, props, and symbols.
```

| 시대 | 지정한 핵심 요소 | 결과 확인 |
|---|---|---|
| 원시 | 흙·암석·화석·공룡 흔적 | 뼈와 발자국은 외곽, 중앙에는 공룡 문양 |
| 중세 | 석조 성채·검·방패·횃불·깃발 | 원형 석재 전투장과 문장 |

### 4.7 영상 생성과 스프라이트 변환

Higgsfield의 **Seedance 2.0 Fast**로 만든 4초 영상을 완성 애니메이션으로 쓰지 않았다. **연속 포즈 후보를 얻기 위한 중간 데이터**로만 사용했다.

| 설정 | 기준 |
|---|---|
| 입력 | 승인된 `*_Chroma.png` 정지 마스터 |
| 길이 | 4초 |
| 카메라 | 완전 고정, 줌·팬·틸트·회전·원근 변화 금지 |
| 동작 | 제자리, 한 번의 연속 샷, 루프 또는 단발 목적 명시 |
| 배경 | 전 프레임 균일 `#00FF00`, 바닥·그림자·반사 없음 |
| 출력 예 | 1280×720, 24 FPS, 97프레임, 약 4.04초 |

**걷기 6포즈의 의미**: F1 접지 A → F2 다운 A → F3 패싱 A → F4 접지 B → F5 다운 B → F6 패싱 B(시작 자세 복귀)

**프레임 수는 대상별로 결정했다.** 기본 걷기는 6프레임이 균형점이지만, 외곽 모듈과 내부 코어가 동시에 움직이는 미래 보스는 8, 반동이 큰 총은 8, 넓은 회전각의 셉터 공격은 10을 사용했다. "보스니까 무조건 프레임 증가"가 아니라 **움직이는 구성요소와 각도 변화**를 기준으로 판단했다.

### 4.8 프레임 분석과 선정

**절차**
- `ffprobe`로 해상도·FPS·프레임 수·길이 확인 → `FFmpeg`로 원본 97프레임 무손실 전개
- 라벨 포함 콘택트 시트로 전체 흐름과 안정 구간 확인, 빠른 공격 구간은 1프레임 단위 재검사
- 형태 변형·모션 블러·장비 소실·배경 얼룩 프레임 제외
- 루프 애니메이션은 마지막→첫 프레임 연결까지 확인

**비연속 프레임 재배열 사례**: 플레이어 부유 영상은 후반에 불꽃이 꺼지고 캐릭터 폭이 변했다. 따라서 **9→15→23→31→22→14**번 프레임을 사용해 안정적인 초기 상승 구간을 핑퐁 순서로 재배열했다. 최종 수평 중심은 x=637.20~637.35로 유지되어 좌우 흔들림이 없었다.

| 대상 | 선정 프레임(0-base) | 권장 FPS | 루프 |
|---|---|---:|---|
| 랩터 달리기 | 24, 28, 32, 36, 40, 44 | 10~12 | 예 |
| 중세 해골 기사 | 24, 28, 32, 36, 40, 44 | 8~12 | 예 |
| 미래 보스 | 3, 14, 24, 35, 45, 56, 66, 77 | 9~11 | 예 |
| Chrono Blaster | 8, 32, 44, 59, 68, 72, 76, 80 | 10~14 | 아니오 |
| Energy Scepter | 0, 13, 21, 30, 39, 41, 59, 69, 75, 78 | 12~14 | 아니오 |

### 4.10 크로마키 제거와 알파 처리

영상 생성 결과에는 알파 채널이 없어 녹색 배경으로 생성한 뒤, 선정 프레임에만 소프트 매트와 디스필을 적용해 RGBA PNG로 변환했다.

```text
remove_chroma_key.py
  --auto-key border
  --soft-matte
  --transparent-threshold 12
  --opaque-threshold 220
  --despill
```

- 영상 압축으로 `#00FF00`이 프레임마다 달라지므로 **테두리 중간값으로 키 색상을 자동 추정**
- 키 색상과의 채널 거리·녹색 우세도를 결합해 소프트 알파 계산
- 반투명 가장자리의 녹색 채널을 줄이는 디스필 적용, 완전 투명 픽셀은 `RGBA=(0,0,0,0)`으로 정규화
- 리사이즈 후 다시 생긴 녹색 우세 보간 픽셀을 추가 검사·제거

**흰색 배경 예외**: 해골 기사 영상은 흰색 배경이었고 검·갑옷 하이라이트·치아도 흰색이라 단순 색상 삭제를 쓸 수 없었다. 바깥 배경과 연결된 흰색만 제거한 뒤, 검·다리·망토·방패 사이의 내부 빈 공간을 별도로 확인해 `Transparent_Refined` 세트로 정리했다.

### 4.11 디자인 파트 자동 검사와 AI 오류 대응

| 검사 | 판정 기준 | 예시 |
|---|---|---|
| 파일 규격 | RGBA, 지정 해상도, 번호 연속 | 10장 모두 1280×720 RGBA |

### 4.12 몬스터·보스 표준과 방향 반전

- 보스 정지 마스터: 1254×1254 RGB PNG, 정확한 `#00FF00` 배경, 가장 긴 실루엣 1028px로 4종 크기 통일
- 수평 기준 유지, 더치 앵글·캔버스 회전 금지
- **프레임 수는 크기가 아니라 움직이는 구성요소로 판단**: 티라노·흑기사·전차형은 6, 외곽 모듈 공전 + 내부 코어 변화가 겹치는 미래 보스는 8
- 좌우 대칭에 가까운 적은 `SpriteRenderer.flipX`로 반대 방향 처리 가능. 다만 검·방패처럼 손이 바뀌면 문제가 되는 비대칭 장비는 별도 승인 또는 전용 방향 제작이 필요하다. **Flip X는 잘못된 보행을 고치지 못하므로 원본 프레임에서 양발 교대가 먼저 완성돼야 한다.**

### 4.13 사운드 — Suno로 만든 시대별 BGM

- 도구: **Suno (Pro 구독)**, 시대별 BGM 4곡 작곡·생성
- 곡 구성: 원시 「돌의 첫 박동」 / 중세 「십자검 성채」 / 현대 「통제 구역 이상」 / 미래 「크로노 가디언」
- 각 시대의 정체성(원시=타악 중심, 중세=현악·합창, 현대=긴장감 있는 전자음, 미래=신스)에 맞춰 생성하고, 루프 재생을 전제로 길이를 51~89초로 정리했다.

>
> 별도 Unity 프로젝트에서 만든 `.anim`은 Sprite GUID와 경로가 달라 참조가 끊긴다.
> 따라서 아트 단계에서는 **PNG와 명세만 전달하고 Animation Clip은 실제 프로젝트에서 생성**하는 방식을 택했다.

## 05 두 파트가 만나는 지점 — 아트를 게임으로 바꾸는 절차

이 장이 2인 팀에서 AI 활용이 실제로 작동한 방식이다. 디자인이 만든 후보를 개발이 그대로 붙인 것이 아니라, **판정·용량·가독성 세 축에서 다시 맞췄다.**

### 5.1 "보이는 것이 곧 판정" — 그림에 히트박스를 맞춘다

프로젝트 전반의 규칙은 **그림이 판정을 따라가는 것이 아니라 판정이 그림을 따라간다**는 것이다.

| 사례 | 아트 | 개발이 맞춘 방식 |
|---|---|---|
| 근접무기 (Energy Scepter) | 휘두르기 10프레임 | 10장의 주축을 2차 모멘트로 실측 → 0°→+27°→−34°→0°, 회전축은 자루의 47% 지점(무게중심 예측 오차 **5px**). 그 각도표를 그대로 코드에 넣어 **홀 그림이 지나간 자리 = 히트박스**(선분 + 굵기 0.14)로 만들었다 |
| 감속 장판 | 원형 아트 | 판정이 사각형이었으나 **원으로 변경**. 원을 그려 놓고 사각으로 맞히는 쪽이 더 나쁜 거짓말이라고 판단(면적은 78.5%로 감소) |
| 매지션 장판 | 원근으로 눌린 타원(가로 53.5% / 세로 37.5%) | 그대로 쓰면 세로 사거리가 절반처럼 보인다 → **원근을 포기하고 세로를 2.14배 늘려 정원으로** 만들어 판정과 일치시킴 |
| 보스 스프라이트 | 시대별 6~8프레임 | 몸통 판정을 그림 크기에 맞춰 재조정 |
| 무기 위치 | — | 플레이어 스프라이트 실측(1.63×1.77유닛)을 근거로 무기를 쥐는 거리를 0.45 → 1.05로 조정 |

### 5.2 아트 프레임 규약을 코드가 그대로 받는다

- 디자인은 **한쪽 방향 그림만** 전달하고, 반대쪽은 `flipX`로 처리한다.
- 시대마다 아트 담당·구도가 달라 방향이 통일된다는 보장이 없으므로, `EraConfig`에 `enemyArtFacesLeft` / `bossArtFacesLeft` 플래그를 세트별로 두었다. 게임에서 적이 진행 방향과 반대로 보이면 **이 값 하나만 뒤집으면 된다.**
- 프레임 장수는 시대마다 달라도 된다(미래 보스 8, 나머지 6). 배열 길이를 그대로 읽는다.
- 컬러 아트가 없는 시대는 기존 틴트 방식으로 자동 폴백된다 — 아트가 순차적으로 도착하는 상황을 전제로 설계했다.

> **곱연산 함정**: `SpriteRenderer.color`는 곱연산이라 컬러 아트에 시대 색을 곱하면
> 그림이 그 색조로 덮인다. 그래서 아트가 있으면 색을 흰색으로 두고, 시대 색은
> `AccentColor`로 따로 넘겨 파편·표식 연출에만 쓴다. 같은 실수를 장판 아트에서 또 겪었다.

### 5.3 용량 예산 — AI가 만든 아트를 WebGL에 넣는 비용

빌드 용량이 곧 로딩 시간이므로, 반입할 때마다 실측 수치를 남겼다.

| 자산 | 원본 | 반입 후 | 처리 |
|---|---|---|---|
| 맵 4종 | 3344×1882 각 13 MB | — | maxTextureSize 2048 + crunch, 맵 1장당 약 4.7 MiB |
| BGM 4곡 | MP3 스테레오 6.4 MB | **2.0 MB** (-69%) | 모노 강제 + Vorbis q0.4, `CompressedInMemory` |
| 메인 배경 | 1672×941 PNG 1.8 MB | **450 KB** | 1280×720(4의 배수)로 축소 → DXT1 |
| 장판 2종 | 1024² / 1536×1024 | **641 KB** | 512² / 768×512 → DXT5 |
| 효과음 16종 | — | **0 byte** | 코드 합성 (RAM 765 KB) |
| 이펙트 텍스처 6종 | — | **0 byte** | 코드 생성 (RAM 96 KB) |

- **4의 배수 크기가 중요하다**: 텍스처 폭·높이가 4의 배수가 아니면 DXT 압축이 걸리지 않아 RGBA32로 떨어진다(1280×713이면 3.6 MB). 그래서 임포트 전에 크기를 맞췄다.
- **여백을 실측해서 스케일을 낸다**: 장판 아트는 프레임에 큰 여백이 있어(그림이 68% / 53.5%) 스프라이트 크기를 그대로 쓰면 보이는 원이 판정보다 32~47% 작다. 알파 24 기준으로 그려진 범위를 픽셀 단위로 재서 상수로 박고 그 값으로 나눈다.
- **회전축은 위치가 아니라 피벗으로 잡는다**: 그림 중심이 프레임 중심과 어긋난 것을 위치로 보정하면 장판이 회전할 때 그만큼 원이 흔들린다(피벗이 곧 회전축이므로). 임포터의 커스텀 피벗으로 해결했다.

### 5.4 사운드 통합 — 생성 AI(BGM) + 코드 합성(SFX)

사운드는 두 방식을 **의도적으로 갈라 썼다.**

| 축 | BGM 4곡 | 효과음 16종 |
|---|---|---|
| 제작 | Suno (Pro) — 디자인 | 코드 합성 — 개발 |
| 이유 | 곡은 사람이 들을 음악이라 생성 AI가 압도적으로 유리 | 16종에 수 MB + 라이선스 표기가 붙는데, 레트로 아케이드 톤이라 합성으로 충분 |
| 빌드 비용 | 2.0 MB | **0 byte** (RAM 765 KB) |
| 크기 설계 | 볼륨 0.5 고정 | 클립마다 최고점을 목표 피크로 **정규화** — 피격 0.95 / 적 피격 0.40 / 총 0.38 / 경험치 0.35 |

- BGM은 시대 전환 시 1초 크로스페이드로 교체되며, **그 시대에 들어갈 때만 로드하고 이전 곡은 즉시 언로드**한다(저사양 브라우저 대비 상시 상주 4곡 회피).
- 타이틀·직업 선택 화면은 무음이고, 판이 시작될 때 BGM이 시작된다. 결과 화면에서는 1.2초 페이드아웃으로 걷어낸다.
- 효과음은 소리별 최소 간격(적 피격 45 ms)으로 한 프레임에 20마리가 맞아도 한 번만 나게 했고, 반복음은 피치를 ±6~10% 흔들어 기계음이 되지 않게 했다.

## 07 확인된 AI의 한계와 완화 방법

### 7.1 생성형 AI (아트·영상)

- 영상 생성 AI는 무기·팔다리·문양을 프레임 사이에서 변형할 수 있다.
- 금지한 투사체·궤적·블룸도 "시각적으로 그럴듯하다"는 이유로 생성될 수 있다.
- 4초 영상의 시작과 끝이 자동으로 루프되지 않으며, 균등 샘플링은 보행 의미를 보장하지 않는다.
- 크로마키 색은 영상 압축으로 흔들리며, 흰색 배경은 캐릭터 내부 흰색과 충돌한다.
- 생성 원화의 크기·방향·시점은 수치 정규화와 별도 QA가 필요하다.

**완화**: 공식 디자인 마스터를 먼저 승인하고 영상은 포즈 후보로만 사용 / 프롬프트에 고정 요소와 실패 유형을 반복 명시 / 전체 프레임 시각화 후 동작 의미 기반 수동 선별 / 원본·최종본·Drafts 분리 / 자동 수치 검사와 배경 합성 시각 검사 병행.

### 7.2 코딩 AI (개발)

- **화면에서만 판단되는 값은 거의 항상 첫 시도가 빗나간다.** 색, 크기, 위치는 캡처 없이 맞출 수 없다.
- **직렬화된 값이 코드 기본값을 덮는다.** `.cs`만 고치고 반영됐다고 판단하면 틀린다(프리팹·씬에 이미 저장된 값이 우선).
- **에디터 도구는 조용히 실패한다.** 빌드를 "failed"로 오보고하거나, 모달 다이얼로그로 세션을 통째로 막는다.
- **계측 대상이 움직이면 단발 스냅샷은 거짓말을 한다.** 게임이 계속 도는 상태에서 한 번 찍어 판단하면 오진한다.
- 리플렉션·파일 삭제 등 일부 경로는 도구 제한으로 아예 막혀 있어 우회 설계가 필요하다.

**완화**: 검증 절차를 프롬프트에 명시 / 규칙 파일(`CLAUDE.md`)에 실패를 규칙으로 승격 / 측정 시 `timeScale=0`으로 대상을 얼린 뒤 실측 / 값이 반영됐는지 `SerializedObject`로 되읽어 확인 / 빌드 성공은 산출물 타임스탬프·바이트로 판정.

## 10 결론

시간관리국에서 우리는 AI를 단독 제작자가 아니라 **통제 가능한 제작 도구**로 사용했다.

- **디자인**은 기준 이미지와 금지 목록으로 생성을 구속하고, 4초 영상을 완성물이 아닌 포즈 후보로만 다루었으며, 알파·중심·잔여색을 수치로 검사한 뒤에야 게임용 PNG로 승격시켰다.
- **개발**은 규칙 파일로 AI의 작업 범위와 금지 API를 상시 고정하고, 코드 작성뿐 아니라 **에디터 조작과 실측 검증까지** AI에 맡기되 Play 모드 수치·화면 캡처·빌드 바이트를 근거로만 결과를 채택했다.
- **두 파트가 만나는 지점**에서는 그림이 판정을 따라가는 것이 아니라 판정이 그림을 따라가게 만들었고, WebGL 용량 예산 안에 들어오도록 반입할 때마다 수치를 남겼다.

따라서 본 프로젝트의 AI 활용은 **생성 횟수가 아니라, 생성 결과를 실제 게임 자산으로 전환하기 위해 설계한 구체적인 지시와 검증 절차**에 의미가 있다. 특히 이 문서에 기록한 실패 사례들 — 모달로 막힌 8분, 전멸한 폰트 참조 11개, 세 번 빗나간 이펙트 색, 얼려 놓아 알파 0이던 장판 — 은 전부 "AI가 됐다고 말한 것"과 "실제로 된 것"이 다른 지점이었고, 그 간극을 메우는 절차가 이 프로젝트에서 AI를 쓸모 있게 만든 실체다.

> **재사용 가능성**
>
> 원거리 몬스터, 추가 공격, 피격·사망, 장판 활성화 애니메이션도 같은 구조를 재사용할 수 있다.
> 달라지는 것은 에셋별 동작 의미와 프레임 수이며, **기준 고정 → 생성 → 선별 → 후처리 → 수치 검증 → 통합** 계층은 동일하다.
